> 生成日期：2026-09-21 ｜ 来源：本项目代码实测 + 2026-07-31 ~ 09-15 的 Cursor 会话记录提炼

## 摘要（30 秒版）

本项目是一套 **A 股量化选股系统**，三条业务主线：**首板战法**（最成熟，早盘选股 + 收盘补价复盘）、**历史数据回填**（慢速补 3 年数据）、**09-新模式「涨停回头低吸」**（独立 Flask 系统）。

每天自动跑的东西分两类：**交易时段内的选股与推送**（早盘 7:50 起到 15:05），**非交易时段的慢速补数**（07:00 / 11:00 / 15:00 / 19:00 四批）。所有对外接口调用都受「**防封号铁纪律**」约束——这是 2026-08-20 Baostock 账号被永久封禁换来的教训。

**三个待处理问题**（详见文末）：① crontab 里 5 条早盘/收盘任务指向**旧目录 `new_stock`**（停留在 7 月代码）；② 两个回填脚本仍在用 Baostock 取成交额，与铁纪律冲突；③ V2 规格书的定时任务表与代码实际不一致。

## 二、三条业务主线

### 2.1 首板战法链路（最成熟）

选股 → 落盘 → 收盘补价复盘。四个程序各跑各的：

| 程序 | 位置 | 干什么 | 产出 |
|------|------|--------|------|
| **stock** | `首板战法/stock/stock.py` | 取前一交易日东财涨停池，筛首次涨停，按综合得分取前二 | `results/{日期}_recommendations.md`、`trades/{买入日}.json` |
| **slow** | `首板战法/slow/slow.py` | 低价「一进二」：ST 股 ≤6 元、非 ST ≤12 元，且要求 10:30 前封板、炸板 ≤1 次、同行业至少 2 家涨停 | `results/{日期}_slow_recommendations.md` |
| **up** | `首板战法/up/up.py` | 强度首板，**D1 早盘集合竞价买入**，四维评分（趋势/未来/情绪/基本面） | `up/strength_limit_up_result.json`（**唯一权威源**） |
| **stock_updata** | `首板战法/stock/stock_updata.py` | stock 的变体，只挑**集合竞价绿开**（今开 < 昨收）的标的 | 同上格式 + 微信推送 |

**交易日口径**：D0 = 涨停（复盘）日，D1 = 次日买入日，D2 = 卖出日（9:35 早盘 / 13:15 午盘两个时点）。

**关键约定**：9:00 早盘只写代码/名称/排名，价格留空；15:00 收盘补全才回填买卖价与盈亏。

### 2.2 历史数据回填链路

慢速补齐近 3 年数据，**四个批次用四种线路**，共用一把全局互斥锁，同一时刻只跑一条。

### 2.3 09-新模式「涨停回头低吸」

独立 Flask 系统（端口 5055），三层池：**涨停池 → 观察池 → 持有池**。只复用首板链路的 `price_service.py` 做行情取数，数据完全独立，**不发微信通知**。

选股核心：主板、股价 <30 元、上市满 5 年、市盈率 <28、连续 2 年分红且分红率 ≥20%、最近 10 天内首次涨停（强制连板数 = 1）、回调到 10 日线与 20 日线之间。

买卖规则：调整第 3–4 天半仓建仓，第 4–5 天阴线/十字星补半仓；**最多同时持有 2 只**；跌破 30 日线或浮亏 ≤ -6% 止损；**持有不超过 7 天，最迟第 7 天尾盘卖出，不看利润**。

## 三、定时任务总表（以 crontab / launchd 实际配置为准）

### 3.1 交易时段（选股与推送）

| 时间 | 跑什么 | 说明 |
|------|--------|------|
| **7:50** | 后台单独启动 `up.py` | up 要分析约 77 只涨停股，耗时最长，先给它抢时间 |
| **8:50** | slow → up → stock 依次跑 | 检测到 up 已在跑就等待，不重复启动 |
| **9:23** | 竞价预热（cron + launchd 双触发） | 拉起 Python，程序内精确等到 **9:24:40** 开扫 |
| **9:24:40** | `stock_updata.py` 开扫 | 逐只请求腾讯，凑齐绿开前二即停 |
| **9:28** | 微信推送 | **硬截止 9:29**，失败短间隔重试 |
| **9:30 / 10:30 / 12:30** | 复检 slow、up 是否产出 | 缺了才重跑，不重复跑 |
| **9:40** | 涨停回头低吸流水线 | 顺序固定：涨停池 → 观察池 → 持有池（先卖后买） |
| **11:25 / 14:30** | 持有池现价监控 | 午盘 / 尾盘各一次 |
| **15:00** | UI 内置收盘补全 | 有早盘文件则只读文件、不重跑脚本 |
| **15:05** | `daily_close_cron_entry.sh` | 与 UI 双保险，**不依赖 UI 进程** |

> **交易日的判定方式**：早盘任务写成「**每天**触发」（`* * * *`），由**脚本内部的 A 股交易日历**过滤——**不能写成周一到周五**，否则节假日、调休会错。

### 3.2 非交易时段（慢速回填，四批四线路）

| 时间 | 线路 | 做什么 | 安全策略 |
|------|------|--------|----------|
| **07:00** | A 纯补价 | 腾讯/新浪逐条补买价卖价 | 不扫市、不登录 Baostock |
| **11:00** | B Baostock 倒序 | 写首板明细 3 天/次 | **全天唯一** Baostock 登录点，串行扫市 |
| **15:00** | C 腾讯正序 | 补 1–7 月空洞 2 天/次 | 禁用 Baostock |
| **19:00** | D 补价 + 查缺 | 补价 + 8–12 月查缺 2 天/次 | 不全市场扫描 |

**自适应配额**：试探期固定 2 天/次；连续 2 次成功升到 3 天/次；异常或单次超 2 小时降到 1 天/次。目标日产量约 7 天明细，稳定后可提到 10 天。

### 3.3 防电脑休眠

- Baostock 线专用：**04:00 自动开启**、**21:30 关闭**（LaunchAgent + Amphetamine）
- 早盘线：**06:55 开启**、**21:35 关闭**
- 每批回填开始前再检查一次，`caffeinate` 兜底；A 股交易日额外保活到 20:00

## 五、取值原理（关键数值怎么算）

### 5.1 涨停与价格

| 数值 | 怎么算 |
|------|--------|
| **涨停比例** | 按代码前缀：创业板/科创板 20%，北交所 30%，其余 10% |
| **涨停价 / 跌停价** | 昨收 ×（1 ± 比例），保留 2 位小数 |
| **是否涨停** | 现价与涨停价偏差在 0.3% 以内即判定涨停 |
| **一字板** | 开盘即涨停，且振幅 ≤0.5%（或开盘=最高=最低） |
| **买入价** | 取 **D1 开盘价**。若 D1 开盘就涨停（买不进），清空全部买卖价并标注原因 |
| **卖出价** | 取 **D2 的 9:35 与 13:15** 两个时点。若 9:35 一字/涨停则跳过该点；若 13:15 仍涨停或跌停，**滚动到下一交易日**，最多滚 8 天 |
| **盈亏** | （卖价 − 买价）÷ 买价 × 100%，保留 2 位；分批口径为两个时点各半仓的平均 |

### 5.2 竞价「绿开」判定

只用 **今开 vs 昨收**：（今开 − 昨收）÷ 昨收。低于 -0.05% 算绿开，高于 +0.05% 算红开。**禁止用现价冒充竞价价**——曾因用错导致红开被当成绿开选入。

### 5.3 09-新模式专有

| 数值 | 怎么算 |
|------|--------|
| **调整第 N 天** | 涨停当日及之前记为 0，次日记 1，以此类推（按交易日算） |
| **持仓第 K 天** | 买入日 = 第 1 天 |
| **均线 MA(N)** | 最近 N 个交易日收盘价的算术平均 |
| **低吸区间** | 20 日线 < 现价 < 10 日线，且 10 日线在 20 日线上方 |
| **止损触发** | 现价跌破 30 日线 **或** 浮亏 ≤ -6% **或** 触及止损价，任一即卖 |
| **近 10 日首次涨停** | 昨日涨停且此前 9 个交易日均无涨停；数据未知时**直接判定不通过**（宁缺勿滥） |
| **补仓加权成本** | （原价 × 原比例 + 补价 × 补比例）÷ 总比例 |

## 六、防封号铁纪律（2026-08-20 事故换来的）

**事故**：早期用 6 个线程并发跑 Baostock，每个线程各自登录一次，账号被判定异常，**最终永久封禁**。

**必须遵守**：

1. **登录一次，全程复用**——同一进程内最多登录 1 次
2. **绝不并发登录**——多线程各自登录必封
3. **日常产出与历史回填隔离**——不得与收盘补全同时大批量拉价
4. **Baostock 不是必需的**——日线/分钟线优先走腾讯、新浪、东财
5. **慢速补数**——禁止一次性跑全年
6. **交易时段（9:30–15:00）禁止跑回填**
7. **腾讯实时行情绝不批量**——每次只请求 1 只，间隔 ≥0.45 秒；早盘按强度序逐只拉，凑齐前二立即停止

**数据源实测结论**：腾讯日线稳定，是补价主通道；同花顺涨停池只保留约近 8 个月；新浪实时当日可用；东财在部分月份缺数据；Baostock 已封禁，禁止批量使用。

**换 IP 是否有用**：结论是**基本没用**。实测本机走代理出口到香港节点后，Baostock 登录直接挂起超时——它走自有 TCP 协议，不跟随系统代理。手机热点相对最干净，但也不建议为回填重新启用。

## 七、通知设计

- **渠道**：PushPlus 推送到本人微信
- **谁发**：**只有** `stock/stock_updata.py` 发通知。slow 和 up **不发**，只把结果落盘（它们是你点「拉取」时快速读取的数据源，重跑反而不准）
- **几点发**：竞价任务目标 **9:28 送达，硬截止 9:29**
- **一致性要求**：推送内容与 15:00 的记录**必须一致**，否则无法对账。为此统一以 up 的权威 JSON 为准，禁止用打分规则不同的脚本覆盖当日结果

## 八、踩过的坑（照这个清单避雷）

| 现象 | 根因 | 怎么修的 |
|------|------|----------|
| 同一只票在两个买入日重复出现 | 一个分析日期的结果同时匹配了两个买入日 | 每个结果文件只对应一个买入日 |
| 周六竟然有交易记录 | 「强制重拉」绕过了交易日历 | 多层防护：写入、落盘、同步、UI 启动各拦一道，强制也不能在非交易日写 |
| 某日 up 没数据 | up 要分析 77 只票需 30–60 分钟，旧超时只有 15 分钟 | 超时逐步放宽到 120 分钟；8:50 提前后台启动；加进程锁禁止重复启动 |
| 5 个 up 进程同时跑全部卡死 | 没有进程锁 | 单实例 + 加锁等待 |
| 页面默认停在 7 月 | 前端用 UTC 时间，比北京时间早 8 小时偏到上个月 | 统一用北京时间；后端把当前月排第一 |
| 选了月份切 Tab 又跳回本月 | 月份状态与下拉框不同步 + 旧请求响应覆盖新请求 | 以页面元素为月份唯一来源；给请求加序号丢弃过期响应 |
| 15:00 补全报错 | 模块导入路径错 + 单条失败拖垮整批 | 改为动态加载；单条加异常保护，失败不中断 |
| slow/up 数据停在某两天 | **不是补价问题**，是没有选股源文件 | 补跑对应日期的选股脚本。**前提是必须有源文件，没有就补不出来** |
| 连板票开板后没补卖价 | 收盘补全只扫「今天+昨天」，更早买入的滚动票漏了 | 改为扫 60 天内所有「计划卖出日已到但卖价仍空」的记录 |
| 涨停池不准（二板三板混入） | 没用东财「连板数」字段；历史数据失败时把「未知」当「未涨停」放行 | 强制连板数 = 1 + 近 10 日涨停池交叉校验；一字板默认排除 |
| 竞价任务完全没跑 | cron 把日志重定向到 `/tmp` 子目录，目录被清理后重定向失败，入口脚本一行都没执行 | **cron 不做外层重定向**，日志写项目内目录并先建目录 |
| 收盘后收益率不刷新 | 只算在内存里没落库 | 卖出时同步落库盈亏字段 |
| cron 突然不跑了 | 电脑睡眠没唤醒 | Amphetamine 定时开启 + `caffeinate` 兜底 |
