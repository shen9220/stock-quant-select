### 三种模式（PushPlus 官方定义，**to 与 topic 不能同时出现**）
| 模式 | 参数 | 含义 | 值格式 |
|---|---|---|---|
| 一对一 | 不填 | 只发给自己 | — |
| **好友消息** | `to` | 发给指定好友 | 32 位 hex 好友令牌 |
| 一对多 | `topic` | 发给群组所有订阅者 | 自己定义的群组编码（短字符串） |

官方原文：「好友消息和群组消息不能同时使用，**请勿同时填写 to 和 topic**」。

### 配置读取（`pushplus_notify.load_pushplus_target()` 返回 `(mode, value)`）
1. 环境变量 `PUSHPLUS_TO` / `PUSHPLUS_TOPIC`
2. `~/new_stock/github/pushplus/topic.md`（与 `token.md` 同级）
   - `TO=xxx` → 好友模式；`TOPIC=xxx` → 群组模式
   - 裸值：32 位 hex 自动识别为好友令牌，否则视为群组编码
3. 都没配 → `mode="self"`（只推自己，**完全向后兼容**）

### 铁律
- **兜底必须写在 `send_pushplus()` 内部**，不能只写在某个调用点 ——
  这样 `stock.py`（选股通知）、`push_top2_result.py`（日报）、
  `push_weekly_result.py`（周报）、`stock_updata.py`（早盘告警）
  四条链路**零改动**自动按「本人+白名单好友」双发。
- **本人永远在收件人列表**；显式传 `to=`/`topic=` 也遵循同一条规则（本人照收，白名单类别额外转发好友）。
- **to 与 topic 严格互斥**：单条 payload 里绝不能同时出现两个键；双发是分两条请求。
- **日志必须打印实际推送目标 + 流水号**（`→ 本人 流水号=xxx`、`→ 好友[87a31c4a…] 流水号=xxx`），
  否则群发没生效时根本排查不出来。
- **配置文件写法宽容**：支持裸值、`TO=`/`TOPIC=`（大小写不敏感，前缀可带说明文字）、
  网页富文本标签 `<span style=...>`、带引号、带行尾注释；空值跳过继续找下一行。
- **验收标准**：拦截 HTTP 后检查 payload —— 好友模式一条有 `to` 键、本人模式一条无键、
  群组模式一条有 `topic` 键；白名单类别会出现「本人+对外」两条。

### 排查：怎么判断值是好友令牌还是群组编码
PushPlus 对两者都会**同步校验**，无效时返回 `code=999`：
- 无效 `to` → `data=接收用户未关联到公众号`
- 无效 `topic` → `data=群组信息不存在`
- **有效值 → `code=200 执行成功`**。所以直接发一次看返回码即可判定。

### 注意
- PushPlus 是**异步投递**：同步返回 200 只代表「服务端收到请求」，
  不代表好友已收到。真实投递状态用 `query_send_result(shortCode, access_key)`
  （需在个人中心 → 接口设置拿 access-key）。
- 好友令牌属于敏感信息，**不要发到公开渠道**。

## 卖出两批独立滚动（2026-10-16 用户确认）——不可再犯

  - 午盘批在 13:15 遇**涨停或跌停** → 卖不出 → 顺延到**下一交易日的 13:15** 再判断；

## 幂等状态文件原子写（2026-10-23 血泪教训）

`daily_close_job._save_state()` 的临时文件名**必须每进程+每线程唯一**，不得写死。

- **原 bug**：`tmp = f"{STATE_FILE}.tmp"` 固定名。
  多线程（UI 调度线程 + 推送线程）或多进程（UI 服务 + 15:05 补跑 CLI）并发写时，
  A 进程 `os.replace` 后 B 进程的 tmp 已消失 → `ENOENT: rename close_job_state.json.tmp`，
  抛错发生在**推送已成功之后**，导致幂等标记没落盘 → **下一轮重复推送**。
- **正确写法**：
  ```python
  tmp = f"{STATE_FILE}.{os.getpid()}.{threading.get_ident()}.tmp"
  with open(tmp, "w", encoding="utf-8") as f:
      json.dump(state, f, ensure_ascii=False, indent=2)
      f.flush(); os.fsync(f.fileno())
  os.replace(tmp, STATE_FILE)
  ```
  配套：读-改-写用进程内 `threading.RLock()` 串行；异常时清理残留 tmp。
- **验收标准**：并发 20 次写 → 错误数 0、state 文件完好、**无残留 .tmp**。

## 行情源失败必须重试，且只缓存成功结果（2026-10-23 血泪教训）

baostock 服务端会限流（"接收数据异常" / "Broken pipe" / login 失败）。
一旦命中，行情查询返回 None，推送就会出空洞（周报里满屏 `--`）。

- **必须加重试**：所有行情取数（`_close_quote()` / `_quote_with_retry()`）**重试 2 次，间隔 1.5s**。
- **只缓存成功结果**：失败结果**不进缓存** —— 否则限流期间的 None 会被永久缓存，
  即使 baostock 恢复也补不回来。
- **口径留空不造数**：补不齐的字段一律 `--`，但**限流恢复后必须重跑补全**，
  不能让空洞长期留在数据里。
- **禁静默降级**：`get_minute_price()` 里 baostock 已启用却取数失败时，
  **禁止降级新浪**（实测 baostock 56.41 vs 新浪 56.46，同一条记录会写出两个价）。
  取不到就返回 None 留空。
